Engineering work mixes judgment with legwork. Before an engineer can answer whether a change is safe, they collect the related requirements, check who owns them, and find the latest evidence. Flow's agent does that legwork with the systems graph as its context.

The same connections that let a person trace Top Speed down to frontal area let the agent answer a question about it.

## Context comes from the graph

A question such as "What needs attention if the Truck's battery capacity rises to 120 kWh?" depends on the recorded requirements, the systems that deliver them, the relationships between them, and the latest verification results.

The agent works from that project context. Its answer is only as complete as the graph. A missing relationship or an unrecorded result is still a gap, and a good request asks the agent to separate what the model supports from what still needs investigation.

Give the task its context: the project, the branch, the items involved, the outcome you want, and what the agent may change.

## Meet engineers in their tools

The agent connects to the tools teams already use, such as Slack, Jira, SharePoint, and code repositories. When information changes in one of them, the people it affects can find out without going looking.

It also works inside those tools. The BMS software engineer changes the battery thermal limits in firmware and opens a pull request in GitHub. Flow reviews the pull request against the requirements. It finds that the new limits, −5 °C to 30 °C, conflict with **Cell Temperature During DC Fast Charging** at 15 °C to 45 °C. It suggests the traceability links the change is missing and names the two people who resolve it: the engineer who owns the code and the engineer who owns the requirement.

The software engineer never has to leave GitHub to know the change needs a conversation.

## Assistance, skills, and automations

These build on one another.

| Capability | What it does | Example |
| --- | --- | --- |
| Chat with the agent | Works through one question or task with you | Find the Truck requirements that lack verification evidence |
| A skill | Saves how a recurring task should be done | Write requirements in the team's "The system shall…" form |
| An automation | Runs configured work when a trigger fires | Review every firmware pull request against the requirements |

A skill captures how. An automation decides when. Chat lets you supply context and refine the request as you go. When the agent imports a review deck, it applies the team's skills so the new requirements follow house rules.

[Skills](/ai-automations/skills) covers creating and scoping skills. Automation setup is covered in the [API automation guides](/api/automations/overview).

## The agent proposes, the owner decides

Treat the agent's answer as the start of an inspection. Follow its references to the items. Review proposed changes in their branch, where they can be compared with the parent before anyone accepts them. Check whether the agent covered the scope you asked for and whether it hit incomplete information.

The agent acts within your permissions. In a connected tool it can take actions that Flow's branch history does not reverse, so scope those tasks with care.

For a recurring task, inspect a few runs before you depend on it, and keep its instructions current as the model and standards change.

Start with a bounded task, check the result, and turn what works into a skill.
